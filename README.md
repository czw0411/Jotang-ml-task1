## 1. 数据可视化与三分划分

![数据与划分](outputs/figures/01_data_splits.png)

`make_moons` 生成的是两个交错的半月形，本身是**线性不可分**的，所以必须有隐藏层才能分开。
`noise=0.2` 让两个月亮在交界处互相渗透——这一点很重要，它决定了这个数据集的准确率上限
**不是 100%**（后面第 4.7 节会定量看到）。

代码 (`mlp_moons/data.py`) 里的划分方式：

```python
X, y = make_moons(n_samples=1500, noise=0.2, random_state=seed)
X_train, X_hold, y_train, y_hold = train_test_split(X, y, test_size=0.4,
                                                    random_state=seed, stratify=y)
X_val, X_test, y_val, y_test = train_test_split(X_hold, y_hold, test_size=0.5,
                                                random_state=seed, stratify=y_hold)
scaler = StandardScaler().fit(X_train)          # 只用训练集拟合！
```

三个子集的职责：

| 子集 | 规模 | 职责 | 允许做的事 | 绝对不要做的事 |
| --- | --- | --- | --- | --- |
| 训练集 train | 900 (450/450) | 更新权重：`loss.backward()` + `optimizer.step()` | 拟合参数、拟合标准化器、拟合任何预处理 | —— |
| 验证集 val | 300 (150/150) | **模型选择**：选超参、选 epoch、早停、判断过拟合 | 反复看、反复用来调参 | 不要用它更新梯度 |
| 测试集 test | 300 (150/150) | **最终一次**的无偏性能估计 | 报告最终指标 | 不要用它调任何东西 |

为什么这样切分能避免数据泄漏：

1. **先切 test，再切 val**，`train_test_split` 不重复抽样，三个集合在索引上互不相交。
2. **stratify=y**：每个子集都保持 1:1 的类别比例，避免"验证集恰好偏某一类"导致指标抖动。
3. **标准化只用训练集拟合**：`StandardScaler` 的均值/方差里如果混进了验证集或测试集的信息，
   就等于把未来信息泄漏进训练（mean/var 是"数据统计量"，属于特征工程的一部分）。
4. **test 只在最后用一次**：它衡量的是"模型上线后在新数据上的表现"，
   一旦用它来挑超参数，它就不再是测试集，而是第二个验证集，指标会偏乐观。

> 诚实说明：本项目为了做对照实验，每个配置都打印了 test 指标并据此做横向比较。
> 严格意义上这已经让 test 参与了一部分模型选择，属于"轻度污染"。
> 更规范的做法是：只看 val 选方案，最后在 test 上跑一次并只报告那一次。
> 这也是为什么我在第 4 节先用 5 个随机种子量化了实验噪声——差异小于噪声的结论一律不下。

## 2. 模型、训练、验证、测试与保存/加载

### 2.1 网络结构

`mlp_moons/models.py` 里是一个可配置的 MLP（隐藏层数、宽度、激活、Dropout、BatchNorm 都能改）：

```python
class MLP(nn.Module):
    def __init__(self, in_dim=2, hidden=64, n_hidden=2, out_dim=2,
                 activation="relu", dropout=0.0, batchnorm=False):
        layers, prev = [], in_dim
        for _ in range(n_hidden):
            layers.append(nn.Linear(prev, hidden))
            layers.append(ACTIVATIONS[activation]())
            prev = hidden
        layers.append(nn.Linear(prev, out_dim))     # 输出 logits，不加激活
        self.net = nn.Sequential(*layers)
```

基线配置：**2 → 64 → 64 → 2**，ReLU，4482 个可训练参数。

### 2.2 训练循环（`mlp_moons/engine.py`）

每个 epoch：打乱索引 → 按 batch 前向 → 算交叉熵 → `zero_grad / backward / step` →
在验证集上评估（`model.eval()` + `torch.no_grad()`）。

核心四行：

```python
logits = model(Xtr[idx])            # 前向
loss   = criterion(logits, ytr[idx])# 交叉熵（内部含 log_softmax + NLL）
optimizer.zero_grad()               # 清掉上一轮累积的梯度
loss.backward()                     # 反向传播，累加梯度到 .grad
optimizer.step()                    # 用梯度更新参数
```

### 2.3 基线结果

![baseline 曲线](outputs/figures/02_baseline_curves.png)

| 指标 | train | val | test |
| --- | --- | --- | --- |
| loss | 0.0668 | 0.0838 | 0.0769 |
| accuracy | 0.9711 | 0.9633 | **0.9833** |
| ROC-AUC | 0.9975 | 0.9960 | 0.9955 |

验证集最好成绩是第 158 个 epoch 的 97.33%，测试集 98.33%（147+148 正确，5 个错误）。
两条 loss 曲线都平滑下降且没有分开，说明这个规模下**没有明显过拟合**。

### 2.4 模型保存与加载

保存的不只是权重，还有配置、架构和指标，方便日后直接复现推理：

```python
torch.save({"state_dict": model.state_dict(),
            "config": cfg.to_dict(),
            "architecture": {"hidden": 64, "n_hidden": 2, "activation": "relu", ...},
            "stats": stats, "history": history}, "outputs/models/baseline.pt")
```

加载时用同样的架构重建模型再 `load_state_dict`，并且**必须在训练后调用 `model.eval()`**，
否则 Dropout / BatchNorm 会处于训练模式，推理结果会变。
本仓库脚本会自动校验：重新加载后对 300 个测试样本的预测与原模型**逐元素比较，结果 True（完全一致）**。

## 4. 对照实验（每次只改一个变量）

所有实验：同一份 6:2:2 划分、同一随机种子、200 epoch，只改动表中标注的那一个变量；
每个配置的都记录测试准确率、训练耗时、参数量和内存占用。

**先标定噪声**：把基线配置换 5 个随机种子（0~4）重跑：

| seed | 0 | 1 | 2 | 3 | 4 | 均值 ± 标准差 |
| --- | --- | --- | --- | --- | --- | --- |
| test acc | 0.9733 | 0.9833 | 0.9900 | 0.9833 | 0.9867 | **0.9833 ± 0.0062** |

也就是说，只换一个随机种子，测试准确率就在 97.3%~99.0% 之间跳，标准差 0.62%。
**下面的对照实验里小于 1% 的差距都不具备统计意义**，只有趋势和量级值得解读。
（想更严格可以跑更多种子做配对检验，或者把 test 从 300 扩大到 3000。）

两组对照：浅网络（2 层隐藏层）和深网络（4 层隐藏层），都固定其它变量：

| gelu | 10.8 | 0.9700 | 0.9567 | 0.9833 |
| sigmoid | 8.5 | 0.9656 | 0.9700 | 0.9900 |

| name (4 层) | ms/epoch | train acc | val acc | **test acc** |
| --- | --- | --- | --- | --- |
| d4+relu | 17.4 | 0.9756 | 0.9567 | 0.9800 |
| d4+tanh | 14.3 | 0.9633 | 0.9700 | 0.9867 |

![激活函数](outputs/figures/ablation_activation_curves.png)
![激活函数-深](outputs/figures/ablation_activation_deep_curves.png)

观察：在这份数据上四种激活的最终准确率都在 96%~99%，**差异全部落在多种子噪声之内**，
不能据此说"sigmoid 比 ReLU 好"。能看出的是更细的差别：

- 收敛速度不同：浅网络里 `gelu` 在第 **4** 个 epoch 就把验证准确率推到 0.98，
  `sigmoid` 要到第 **73** 个 epoch 才到 0.9733，`tanh` 在第 32 个 epoch 到 0.9733——
  这正是"梯度是否容易消失"的直观体现（详见第 7 节第 1 问）。
- 计算开销：`gelu` 比 `relu` 慢约 6%（10.18 → 10.81 ms/epoch），`relu` 是最便宜的非线性。
- 但**换到 4 层网络，收敛顺序完全变了**：达到最好验证成绩的 epoch 分别是
  `gelu` 46、`sigmoid` 111、`tanh` 165、`relu` 193。既然排序会随深度翻转，
  说明在这个规模（1.3 万参数、900 个训练样本）上，激活函数的差异更多来自优化路径的随机性，
  而不是稳定的结构优势。**这本身就说明：小数据集上的小差异不要过度解读。**

| --- | --- | --- | --- | --- | --- |
| lr=1e-4 | 9.4 | 0.9633 | 0.9700 | 0.9800 | 194 |
| lr=1e-3 | 10.0 | 0.9722 | 0.9633 | 0.9833 | 23 |
| lr=1e-2 (基线) | 10.1 | 0.9711 | 0.9633 | 0.9833 | 158 |
| lr=1e-1 | 11.5 | **0.9422** | 0.9200 | **0.9400** | 60 |

![学习率曲线](outputs/figures/ablation_lr_curves.png)

观察（正好对应第 7 节第 5 问）：

- `lr=1e-4`：曲线极慢，200 epoch 时最好的验证成绩出现在第 194 个 epoch，还在爬升——
  没训练完，属于**欠拟合**状态。
- `lr=1e-2`左右最舒服：20 个 epoch 内就收敛到 95%+。
- `lr=1e-1`：loss 曲线剧烈震荡，最终训练准确率反而最低（0.9422 < 0.9711），
  测试准确率掉到 94%。这就是**步长过大导致在最优点附近反复横跳**的典型现象。

### 4.6 batch size

| name | ms/epoch | train acc | val acc | **test acc** |
| --- | --- | --- | --- | --- |
| bs=16 | 37.7 | 0.9711 | 0.9567 | 0.9767 |
| bs=64 (基线) | 10.7 | 0.9711 | 0.9633 | 0.9833 |
| bs=256 | 2.8 | 0.9733 | 0.9600 | 0.9767 |
| bs=900 (全批量) | 1.0 | 0.9700 | 0.9700 | 0.9833 |

![batch size](outputs/figures/ablation_batch_bars.png)

观察：**准确率几乎不受影响，但速度差 36 倍**（37.7 ms/epoch → 1.0 ms/epoch）。
小 batch 每个 epoch 要做的 Python 层循环多得多，在这个小模型上是纯开销；
大 batch 的代价是梯度噪声小、更新次数少（每 epoch 只有 1 次），
实际训练常常要靠提高学习率来补偿——这就是"线性缩放规则"的由来。

观察：这是**唯一一个能把准确率从 100% 拉到 85% 的因素**。

任何模型都不可能分对（这部分是标签/数据本身的不确定性，叫**贝叶斯误差**）。
所以"模型准确率上不去"要先问：是模型不行，还是数据本身有噪声上限？

### 4.8 训练成本汇总（独立子进程测量）

在同一个进程里连着跑很多实验，进程峰值内存只会单调上升，横向比较不公平，
所以 `scripts/measure_resources.py` 给每个配置开一个**全新子进程**再测：

| 配置 | params | 参数体积 | ms/epoch | 训练 200 epoch | 进程峰值 RSS | 相对"仅导入 torch"的增量 |
| --- | --- | --- | --- | --- | --- | --- |
| 仅导入 torch（不训练） | — | — | — | — | 296.6 MB | 0 |
| w16 | 354 | 0.0014 MB | 10.2 | 2.04 s | 370.3 MB | +73.7 MB |
| w64 (基线) | 4482 | 0.017 MB | 9.1 | 1.82 s | 371.6 MB | +74.9 MB |
| w256 | 67074 | 0.256 MB | 25.7 | 5.15 s | 377.4 MB | +80.8 MB |
| d1 | 322 | 0.0012 MB | 7.8 | 1.55 s | 371.3 MB | +74.7 MB |
| d4 | 12802 | 0.049 MB | 18.4 | 3.69 s | 371.6 MB | +75.0 MB |
| bs16 | 4482 | 0.017 MB | 36.0 | 7.19 s | 371.0 MB | +74.4 MB |
| bs256 | 4482 | 0.017 MB | 2.7 | 0.53 s | 371.7 MB | +75.1 MB |
| bs900 (全批量) | 4482 | 0.017 MB | 1.0 | 0.20 s | 372.4 MB | +75.8 MB |

几点说明：

- **显存（GPU）在本次实验中无法测量**：这台机器 `torch.cuda.is_available() == False`，
  代码里已经接好 `torch.cuda.max_memory_allocated()`（`engine.gpu_memory_mb()`，无 GPU 时返回 -1）。
  在 GPU 上这个网络连 1 MB 显存都用不到，瓶颈完全在 kernel 启动开销，而不是容量。
- **内存主要被框架本身吃掉**：torch 运行时 297 MB，训练一个 4482 参数的小模型只多加 75 MB；
  把参数量放大 15 倍（w64 → w256）也只多 5 MB。也就是说在这个规模上，"内存"根本不是约束，
  **时间才是**——而时间的大头是 Python 层循环次数（batch 越小越慢），不是矩阵乘法。
- 同一配置在不同批次测量会差 10%~50%（例如 w256 在同一进程里测是 17.7 ms/epoch，
  单独开进程测是 25.7 ms/epoch；机器负载和 CPU 调频都会影响），所以绝对值只能看量级。

| **true 0** | 147 | 3 |
| **true 1** | 2 | 148 |

两类错误很对称（FP=3, FN=2），类别 1 的 precision/recall 分别是 98.0% / 98.7%，
macro-F1 = 0.9833。样本是均衡的，所以 accuracy 在这里是可信的指标。

![错误样本](outputs/figures/05_error_samples.png)

被分错的 5 个测试样本（按"错得有多自信"排序，`logit_margin` 越大代表模型越笃定）：

| # | x1 | x2 | 真实 | 预测 | P(真实类) | P(预测类) | \|logit 差\| | 到边界距离 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.191 | 1.072 | 1 | 0 | 0.00002 | 1.000 | 10.99 | 0.500 |
| 2 | -0.271 | 0.266 | 0 | 1 | 0.149 | 0.851 | 1.75 | 0.351 |
| 3 | 1.031 | -0.100 | 1 | 0 | 0.222 | 0.778 | 1.25 | 0.278 |
| 4 | 0.220 | 0.645 | 0 | 1 | 0.447 | 0.553 | 0.21 | 0.053 |
| 5 | 0.148 | 0.669 | 0 | 1 | 0.497 | 0.503 | 0.011 | 0.003 |

这 5 个点可以分成两类，正好对应两种完全不同的"错"：

1. **#1 是数据噪声造成的、本质无法挽回的错误。** 它的坐标 (0.19, 1.07) 深深落在
   上方月亮的弧线上，模型给它的 P(1)=2e-5，几乎"斩钉截铁"地判成 0 类。
   回头看第 1 节的数据图就知道，1.07 这个高度上的点绝大多数属于 0 类（下面那支月亮，
   因为 `noise=0.2` 被推上来了）——**是数据本身把它放错了位置**，不是模型的问题。
   这类点就是"贝叶斯误差"，再大的模型也救不回来。
2. **#4、#5 是边界模糊点。** 它们的 P(1) 分别是 0.553 和 0.503，几乎贴在 0.5 上，
   到边界距离只有 0.05 / 0.003。模型其实"没把握"，这类错误换个随机种子就会翻转
   （这也解释了第 4 节为什么种子间标准差有 0.6%）。

实践含义：

- 评估模型时不能只看错误数量，要看**错误的自信程度**。如果大量错误都是高置信度错误，
  说明训练数据里存在标注错误或分布漂移（#1 这种），值得回去查数据；
  如果错误都贴着边界（#4/#5），说明模型已经接近这个数据集的性能上限。
- 对边界附近的样本，"准确率"这个硬指标本身就不稳定；医疗、风控这类场景应该保留概率输出，
  对 0.4~0.6 区间交给人工复核，而不是硬判。

## 6. 三个额外演示

### 6.1 不清空梯度会怎样

![梯度累积](outputs/figures/grad_accumulation.png)

| 配置 | final train loss | train acc | best val acc | **test acc** | 测试集混淆矩阵 |
| --- | --- | --- | --- | --- | --- |
| 正常 `zero_grad()` | 0.0668 | 0.9711 | 0.9733 | **0.9833** | TN=147, FP=3, FN=2, TP=148 |
| 删掉 `zero_grad()` | 3.2741 | 0.8167 | 0.9300@8 | **0.8333** | TN=150, FP=0, FN=50, TP=100 |

梯度会一直累加，等效学习率随 step 数不断增大，训练很快失控（loss 3.27，是正常值的 49 倍）。
更细节地看：模型最后**退化成了"几乎全判 0 类"**——FP=0、FN=50、少数类 recall 只有 0.667。
注意它的 best val acc 出现在第 8 个 epoch（0.93），之后一路崩坏，这正是"梯度爆炸"的典型样貌。

### 6.2 类别不均衡

用 `make_imbalanced_splits()` 把多数组:少数组做成约 **10:1**（train 1200:133，test 400:45）：

| 方案 | accuracy | balanced acc | 少数类 recall | 少数类 precision | macro-F1 | FN | FP |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 普通交叉熵 | **0.9843** | 0.9419 | 0.8889 | 0.9524 | 0.9554 | 5 | 2 |
| 类别加权 `weight=balanced` | 0.9663 | **0.9615** | **0.9556** | 0.7679 | 0.9162 | 2 | 13 |

![不均衡混淆矩阵](outputs/figures/imbalance_confusion.png)
![不均衡曲线](outputs/figures/imbalance_curves.png)

关键点：**如果模型偷懒，把所有样本都判成多数类，也能拿到 400/445 = 89.9% 的准确率。**
也就是说 98.4% 的 accuracy 里有 89.9% 是"白送"的，真正体现模型能力的是 balanced accuracy、
少数类 recall 和 macro-F1。加权之后 accuracy 掉了 1.8 个百分点（看起来"变差"了），
但少数类漏检从 5 个降到 2 个，balanced accuracy 反而从 0.9419 升到 0.9615。
代价是 precision 从 0.95 掉到 0.77——**加权就是把决策边界往多数类那边推，用更多误报换更少漏报**，
这类取舍要和业务成本一起看，不存在"哪个绝对更好"。

### 6.3 故意过拟合（以及怎么判断过拟合）

配置：把训练集缩到 **30 个样本**，模型放大到 **256×3 隐藏层（132866 参数）**，训练 2000 epoch，
不做任何正则。第二个实验额外把其中 **20% 的标签随机翻转**，人为制造"不可学的噪声"。

![过拟合曲线](outputs/figures/overfit_curves.png)
![过拟合边界](outputs/figures/overfit_boundary.png)

| 实验 | train acc | val acc | val loss | test acc | train-test gap |
| --- | --- | --- | --- | --- | --- |
| 30 个样本，无噪声 | **1.0000** | 0.9400 | 0.9056 | 0.9700 | +0.0300 |
| 30 个样本 + 20% 标签噪声 | **1.0000** | 0.7133 | **16.7390** | 0.6967 | **+0.3033** |
| 同上 + weight decay 5e-2 + dropout 0.2 | 0.8333 | 0.8300 | 0.4416 | 0.8367 | -0.0033 |

我是怎么判断它过拟合的：

1. **训练准确率 100%，而验证准确率只有 71%**，两者差 30 个百分点——这是最直接的证据。
2. **训练 loss 继续下降，验证 loss 却掉头向上**，最后飙到 16.74（正常值是 0.08 量级）。
   验证 loss 的拐点（第 1 个 epoch 附近的 0.8567 是最好成绩）就是"该早停了"的位置。
3. **决策边界变成了"岛屿"**：看 `overfit_boundary.png`，为了迁就 30 个点（其中 6 个标签还是错的），
   边界长出了好几块孤立的红/蓝小区域。这些区域没有任何统计意义，纯粹是在背样本。
4. **测试集掉到 0.6967**，比什么都不做按多数类猜（0.50）好不了多少。

加上 weight decay 和 dropout 之后，模型**放弃了背下那几个错标签**：训练准确率掉到 0.8333
（= 25/30，正好等于 30 个样本里去掉 5~6 个噪声标签后能学到的比例），
但验证 loss 从 16.74 降到 0.44，测试准确率从 0.6967 回到 0.8367，泛化 gap 几乎归零。
**"训练准确率下降"在这里是好消息**——它说明模型不再记忆噪声了。

怎么主动制造过拟合（第 7 节最后一问的答案，全部已在上面验证）：
① 训练样本尽量少；② 模型尽量大；③ 训练轮数尽量多（不给早停）；
④ 加标签噪声；⑤ 关掉所有正则化（weight decay / dropout / 数据增强）；⑥ 学习率不要太小。

## 7. 趁热打铁：问答

### Q1 选择了什么激活函数，为什么？

选 **ReLU**（`nn.ReLU`，段内 `max(0, x)`）。理由：

1. **不饱和**：x>0 时导数恒为 1，梯度不会像 sigmoid/tanh 那样在两端被压到接近 0，
   深层网络更容易训练。本实验里能看到它的实际收益：浅网络中 `sigmoid` 要到第 73 个 epoch
   才把验证准确率推到 0.97，而 `gelu` 第 4 个 epoch 就到了 0.98。
2. **计算便宜**：只需要一次比较，`gelu`（带 erf/tanh 近似）在我的测量里单 epoch 慢 6%~19%。
3. **稀疏激活**：约一半神经元输出为 0，天然带一点正则效果。

它的缺点是 x<0 时梯度为 0，可能出现"死亡神经元"；本任务小、数据简单，没有观察到这个问题。
如果换成更深或者更容易发散的网络（比如 Transformer），我会直接用 **GELU**：它更平滑、
在 0 附近可导，工程上更稳；如果数据是负值为主或者需要严格有界输出，会考虑 tanh。

> 但要诚实：在这份数据上四种激活的**最终**准确率差异（96%~99%）都落在种子噪声 0.62% 之内，
> 所以真正被实验支持的是"收敛速度和计算成本"的差异，而不是"最终精度"的差异。

### Q2 选择了什么损失函数？如果是三分类呢？

选 **`nn.CrossEntropyLoss`**（交叉熵）。理由：

1. **它是分类问题的最大似然估计**：最小化交叉熵等价于最大化"模型认为真实类别正确的概率"，
   有清晰的概率解释。
2. **和 Softmax 组合后梯度极其干净**：∂L/∂logits = `p - onehot`，
   没有额外的饱和因子，所以即使预测得很错，梯度仍然有足够大小推动它回来。
3. **PyTorch 的 `CrossEntropyLoss` = `LogSoftmax` + `NLLLoss`**，
   内部做了 log-sum-exp 的数值稳定处理，比手动 `softmax` 再取 log 安全。
4. 它接收**整数标签**（`y` 直接是 0/1/2），不需要自己 one-hot。

如果这题变成**三分类**：

- 损失函数**不用换**，还是 `CrossEntropyLoss`；只需要把输出层从 `nn.Linear(64, 2)`
  改成 `nn.Linear(64, 3)`，标签继续用整数 0/1/2。它本来就是为 C 类设计的（C=2 就是二分类）。
- 要跟着改的是：数据生成（`make_moons` 只有 2 类，得换 `make_blobs(n_features=2, centers=3)`
  或 `make_classification(n_classes=3)`）、指标（二分类的 AUC 要换成 macro/micro OVR AUC），
  以及混淆矩阵从 2×2 变成 3×3。本仓库的 `classification_metrics()` 目前写死了 `labels=[0,1]`
  和 `pos_label`，迁移到多分类时需要改成 `average="macro"` 的版本。
- 只有在做**多标签**分类（一张图可以同时是"猫"和"狗"，各类独立）时，才换成
  `BCEWithLogitsLoss`（输出维度 C，标签是 one-hot/多热向量，每个输出各自做一次二分类）。

### Q3 `optimizer.zero_grad()`、`loss.backward()`、`optimizer.step()` 分别做了什么？

| 调用 | 做的事 | 不写会怎样 |
| --- | --- | --- |
| `optimizer.zero_grad()` | 把 `param.grad` 清零（默认 `set_to_none=True`，直接置 None） | 见下 |
| `loss.backward()` | 从 loss 出发做反向传播，把 ∂loss/∂param **累加**到 `param.grad` 上（注意是累加，不是覆盖） | 没有梯度，`step()` 什么也不会更新 |
| `optimizer.step()` | 读取 `param.grad`，按优化器规则（Adam/SGD…）就地更新 `param.data` | 参数永远不变，loss 不下降 |

PyTorch 的 `.grad` 是**累加**语义，`backward()` 本身不会帮你清零。所以标准的顺序是：
`zero_grad() → forward → loss → backward() → step()`。

**不清零的后果我实测了**（第 6.1 节）：梯度会把这一轮和之前所有轮加起来，
等效于学习率随 step 数不断放大，200 个 epoch 后训练 loss 从 0.067 涨到 3.27，
模型退化成"几乎全判多数类"，测试准确率从 98.3% 掉到 83.3% 并继续崩。

例外：**梯度累积（gradient accumulation）**就是故意不清零——显存放不下大 batch 时，
把 `batch_size=16` 的数据分 4 次 forward/backward、只在最后 `step()` 一次并清零，
等价于 batch_size=64。这时"不清零"是特性，不是 bug。

### Q4 更深、更宽的神经网络一定能取得更好的效果吗？

**不能。** 本实验的直接证据（第 4.1、4.2 节）：

- 宽度 4 → 256，参数 42 → 67074（**1600 倍**），测试准确率 0.9800 → 0.9767（不升反降）。
- 隐藏层 1 → 4，参数 322 → 12802，测试准确率 0.9800 → 0.9800（完全没变），单 epoch 时间翻倍。

原因是**模型容量必须和任务复杂度、数据量匹配**：

- **过于简单（欠拟合）**：容量不足以表达数据里的真实规律，训练 loss 和验证 loss 都降不下去。
  比如 `w4`（42 个参数）虽然能到 98%，但再复杂一点的分界它就会学不会；
  本仓库的 `lr=1e-4` 实验也展示了另一种欠拟合——不是模型不够大，而是**没训够**。
- **过于复杂（过拟合）**：参数远比数据点多时，模型有能力把训练样本（包括噪声和错标签）
  逐个记住。第 6.3 节里 132866 个参数去拟合 30 个样本，训练准确率 100%，
  验证 loss 却飙到 16.74、测试准确率掉到 0.6967。它学到的不是规律，是样本本身。

正确的做法不是"越大越好"，而是**在验证集上做模型选择**：容量只要能覆盖任务复杂度即可，
再靠正则化（weight decay / dropout / 早停 / 数据增强）把多余的容量压住。

### Q5 学习率过大或过小会怎样？从 loss 曲线能观察到什么？

| | 现象 | loss 曲线特征 | 本实验对应 |
| --- | --- | --- | --- |
| 太小 | 收敛极慢，训练结束时还没训完（欠拟合） | 平滑单调下降，但斜率一直很小，200 epoch 时仍在下降 | `lr=1e-4`：最好的验证成绩出现在第 **194** 个 epoch，还在爬 |
| 合适 | 快速下降后进入平台 | 前 10~30 个 epoch 快速下降，之后平缓 | `lr=1e-2`：20 个 epoch 内到 95%+，最终测试 98.3% |
| 太大 | 在最优点附近震荡甚至发散，最终效果反而变差 | 曲线**锯齿状剧烈抖动**、出现尖峰、不再单调下降，甚至上升 | `lr=1e-1`：训练准确率只有 0.9422（四个里最低），测试 94.0% |

判断技巧：把 loss 曲线**取对数纵轴**或者看前 10 个 epoch 的斜率来判断是否太慢；
看曲线的**方差**（是否上下抖）来判断是否太大。更工程化的做法是学习率扫描
（比如 1e-5 → 1e0 每步乘以 1.2，画 loss-学习率曲线，取下降最快的一段）。

两个容易混淆的细节：

1. **loss 抖动 ≠ 一定太大**：小 batch 的梯度噪声也会造成抖动。
   这个实验里 bs=16 的曲线明显比 bs=900 抖，但最终准确率并不差——抖动幅度和"是否发散"要分开看。
2. **验证 loss 开始上升、而训练 loss 继续下降**，那是过拟合，不是学习率太大（第 6.3 节）。

### Q6 类别不均衡时模型会怎样？为什么？说明了什么？

见第 6.2 节的实验。结论是：

**模型会倾向于预测多数类，少数类被大量漏检，但 accuracy 看起来仍然很漂亮。**

原因是交叉熵是**按样本平均**的：

$$L = -\frac{1}{N}\sum_{i=1}^{N} \log p_{y_i}$$

当多数类占 90% 时，"把所有样本都判成多数类"就已经能让 loss 降得很低、accuracy 拿到 89.9%。
梯度是被多数类样本主导的，模型去拟合少数类的**收益太小**，
在"降低总损失"这个目标下，牺牲少数类是最省力的解。

这说明三件事：

1. **accuracy 在不均衡数据上是失效甚至有害的指标**。本次实验里 98.4% 的准确率，
   其中 89.9% 是"白送"的。
2. **要看少数类的 recall / F1、balanced accuracy、ROC-AUC 或 PR-AUC**，
   并且一定要**打印混淆矩阵**——它一眼就能看出"模型是不是只会猜多数类"。
3. **缓解手段有三类**，本次验证了其中一类：
   - 损失加权（`CrossEntropyLoss(weight=...)`）：少数类漏检 5→2 个，
     balanced accuracy 0.9419→0.9615，代价是误报变多（FP 2→13）；
   - 重采样：对少数类过采样（SMOTE）或对多数类欠采样，让每个 batch 大致均衡；
   - 阈值调整 / 换指标：不硬判 0.5，而是按业务成本选一个阈值，
     或者干脆改用 PR-AUC 来选模型。

> 注意：这三种方法都不会"凭空产生信息"，它们改变的是**决策边界的偏向**。
> 真正的解法仍然是拿到更多少数类样本。

### Q7 如果想要过拟合这个数据集，你会怎么做？怎么判断？

做法（全部在第 6.3 节实测过，并成功把验证 loss 从 0.44 推到 16.74）：

1. **减少训练数据**：1500 → 30 个样本。这是最有效的一招，参数/样本比直接爆表。
2. **放大模型**：64×2（4482 参数）→ 256×3（132866 参数），给它足够的记忆力。
3. **训练足够久**：200 → 2000 epoch，并且**不加早停**，让它把噪声也磨进去。
4. **注入噪声**：把 20% 的训练标签随机翻转，制造"无论如何都学不对"的样本——
   这一条把测试准确率从 0.9700 打到 0.6967。
5. **关掉所有正则**：`weight_decay=0`、`dropout=0`，不做数据增强，不做 early stopping。
6. **（可选）提高学习率**，让它更快地去拟合难样本。

判断过拟合的证据（按可靠性排序）：

1. **训练准确率 ≈ 100%，验证/测试准确率明显更低**，gap 持续扩大（本次 +30.3%）。
2. **验证 loss 先降后升，训练 loss 一直降**——两条曲线出现"剪刀差"，
   验证 loss 的最低点就是该早停的位置。
3. **决策边界出现孤立的碎块/岛屿**，为了迁就个别点而扭曲整体形状。
4. 训练 loss 能降到接近 0，但验证 loss 停在很高的水平（本次 16.74）。

反过来说，**"训练准确率不是 100%"并不一定是坏事**：加上正则后训练准确率降到 0.8333，
但验证 loss 0.44、测试准确率 0.8367，泛化 gap 归零——模型不再记忆噪声，这才是我们要的。

## 9. 局限与可改进

1. **测试集被重复使用**：每个对照配置都看了 test，严格的模型选择应该只用 val，
   test 只在最后报告一次。
2. **每个配置只跑了一个种子**：组间 <1% 的差异无法判定显著（基线种子标准差已达 0.62%），
   更严谨的做法是每个配置跑 5~10 个种子做均值±标准差 + 配对检验。
3. **没有 GPU，显存没法真正测量**：代码里预留了 `torch.cuda.max_memory_allocated()`，
   换到 GPU 机器上就能直接得到显存峰值。
4. **数据只有 2 维**：决策边界可以画出来，这是教学上的优势；
   但也意味着很多结论（比如"宽度没用"）不能直接推广到高维数据。
5. **没有做早停**：本仓库固定跑满 200 epoch。
   实际训练中按验证 loss 做 early stopping，是性价比最高的一招。
